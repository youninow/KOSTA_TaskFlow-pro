## 읽는 순서

```
00-overview  →  01-product  →  02-specs  →  03-design  →  04-tasks  →  05-conventions
    (지도)         (목표)        (구조)        (화면)        (일정)         (규칙)
```

작업 시작 전 반드시 이 순서를 따른다.
앞 문서를 읽지 않으면 뒤 문서의 결정이 왜 그렇게 내려졌는지 맥락을 잃는다.

---

## 왜 이렇게 나누는가 — 관심사 분리 원칙

소프트웨어 설계의 핵심 원칙인 **관심사 분리(Separation of Concerns)** 를 문서에도 동일하게 적용한다.

하나의 문서가 "무엇을 만드는가", "어떻게 만드는가", "어떻게 협업하는가"를 모두 담으면 다음 문제가 생긴다.

- **변경 범위 과대**: 기능 하나 바뀌면 전체 문서를 뒤져야 한다.
- **역할 혼선**: 기획자가 읽을 내용과 개발자가 읽을 내용이 섞인다.
- **추적 불가**: 어떤 결정이 왜 내려졌는지 히스토리가 묻힌다.

6개 파일은 각각 **정확히 하나의 질문**에만 답한다.

| 문서 | 답하는 질문 |
|------|------------|
| `01-product` | 무엇을 왜 만드는가? |
| `02-specs` | 어떤 구조로 만드는가? |
| `03-design` | 사용자에게 어떻게 보이는가? |
| `04-tasks` | 언제 무엇을 만드는가? |
| `05-conventions` | 어떤 규칙으로 함께 만드는가? |

이렇게 분리하면 기획이 바뀌어도 `01-product`만 수정하면 되고,
기술 스택이 바뀌어도 `02-specs`만 열면 되며,
새 팀원이 합류해도 읽는 순서가 명확하다.
